# 版本计划：v1.1 → v2.0 → v3.0

> 写于 2026-10-20，在动手之前；同一天按自查改过一次（第 2 节 D7–D8、第 5 节整节）。依据有三样：v1.0 和 v1.1 的考试结果（[`external_plan.md`](external_plan.md)、[`temporal_plan.md`](temporal_plan.md) 第 8–9 节；笔记第 28、29 章），已有逐题结果上的上限分析（第 29 章第 7 步），和同类论文的做法（出处在最后）。
>
> 这是路线图，不是考试方案。每个版本的考试方案照旧另写一份，考前提交。这里写的成功标准，到那时可以写得更细，但不放宽。

## 1. 现在在哪

| 版本 | 改了什么 | 能算数的成绩 | 没解决的 |
|---|---|---|---|
| v1.0（已打标签） | `seeded-agent`：开局带固定流程的证据 | 留出集 42.4%，固定流程 36.8%（57 : 10）；时间外推 23.4%，直接猜 8.5%（9 : 2，p = 0.065，没过线） | HMS、RAMEDIS 上显著输给直接猜（4 : 15、47 : 97） |
| v1.1（代码 `788e56e`） | `hypothesis-agent`：模型先凭自己的知识列出怀疑的病；两份名单同等看待；每个候选标上患病率 | 时间外推 25.5%（10 : 2，p = 0.039，过线）；留出 200 道 45.0%（v1.0 43.0%）；MME 72.5% | MME 上比 v1.0 少对 3 道（1 : 4）；HMS、RAMEDIS 已改作练习卷 |

一句话：v1.1 修好了"模型认识的病被工具压下去"，但在能算数的外部卷上，还没有证明比 v1.0 好。

## 2. 不足之处

八条。每条写三件事：看到了什么、原因在哪、别人怎么做。

### D1 答案只能是 OMIM 里的病

- **看到的**：HMS 88 道里有 24 道，任何用我们知识库的系统都是 0 分，比如抗合成酶综合征、IgA 血管炎
- **原因**：[`knowledge/hpo.py`](../src/raredx/knowledge/hpo.py) 读 HPO 的标注文件时，只留 `OMIM:` 开头的行。同一个文件里还有 Orphanet 整理的 4,355 种病、116,661 行标注（占全部标注的四成），全被丢掉了。抗合成酶综合征就在里面（`ORPHA:81`，44 条症状）
- **别人**：DeepRare 用病名作答，再由裁判判对错，不受编号限制；Monarch、ClinGen 用 Mondo 疾病本体把 OMIM、Orphanet 的编号对齐

### D2 只算"像不像"，而且只有一张表可查

- **看到的**：v1.0 在 HMS 上常把相对常见的病，换成一个症状更"对得上"的少见病（红斑狼疮 → PLD4 相关狼疮，白塞病 → ADA2 缺乏症）
- **原因**：`rank_diseases`、`check_match`、`lookup_disease` 查的是同一张表，而表里 OMIM 部分给相对常见的病标得很少。同一个病，Orphanet 标得多得多（HPO v2026-09-01 里的症状标注行数）：

  | 病 | OMIM | Orphanet |
  |---|---|---|
  | 系统性红斑狼疮 | 21 | 44 |
  | 白塞病 | 15 | 85 |
  | 肉芽肿性多血管炎 | 32 | 80 |

- **v1.1 已经做的**：模型先自己答；每个候选标上患病率。方向对了，但工具本身没改
- **别人**：DeepRare 的怀疑名单来自三个互相独立的来源（两个外部症状排序工具，加上模型自己），再查病例库和 PubMed；liteOdyssey 查 Monarch、ClinGen、gnomAD、PubMed

### D3 主要问题问得太窄

- **看到的**：留出集上 agent 对固定流程 57 : 10，外部卷上 54 : 45（不显著）
- **原因**：输入是一份固定的 HPO 列表，agent 能自己决定的只有"先查什么、后查什么"。所有查询又都落在同一张表上，固定流程把这些也都查了，两者差别自然很小
- **别人**：主要的比较对象是**同一个模型不用工具**，再加一个成熟工具。比较多种 agent 结构的论文发现，单 agent 48.5%、层级式多 agent 50.0%，几乎一样。SDBench 认为 agent 的价值在"决定还要收集什么信息"

### D4 开发和验证出自同一个地方

- **看到的**：开发只在 dev-200 上做，留出集也来自 Phenopacket Store：论文不重复，但整理的人、写法、病的类型（发表过的单基因病）都一样，和 HPO 标注的来源也一样。留出集按患病率分，最常见那一档只有 42 道（5%），这一档上模型直接猜（61.9%）已经比 agent（57.1%）高。HMS 的病人大多在这一档，所以 v1.0 在 HMS 上输，事先看得出来
- **原因**：系统一直在一类病人上调，养成的习惯（"挑最对得上的罕见病"）换一类病人就不对了。HMS、RAMEDIS 整份当考卷用，考完读了错题，只能改作练习卷，手上就没有干净的外部卷了。RareBench 2024 年就公开了，deepseek 很可能背过这些题
- **别人**：liteOdyssey 开发只用 50 道，测试用开发时没见过的病；真实病人（UDN 的 515 人）在**考之前**就切开：50 道用来调，465 道留着考。DeepRare 在九组数据上报，其中四组来自医院

### D5 判分：宽松判分的裁判和 agent 是同一个模型

- **看到的**：DeepRare 对 agent 的结论，在严格判分和宽松判分下正好相反
- **原因**：宽松判分的裁判是 `deepseek-flash`，正是 agent 用的模型，可能偏向自己的说法
- **别人**：liteOdyssey 用另一家公司的模型当裁判，再用编号判分核对，最后请两位医生盲评 120 道

### D6 有基因时的考法太简单

- **看到的**：有基因时，agent 自己和"按基因排名"打平（dev-200：62.5% 对 62.0%），领先全靠把两份排名合并
- **原因**：现在的模拟是"真基因混在 49 个随机基因里"，只有基因名，没有变异。真实的测序结果是成百上千个变异，大多数一看就能排除，难的是剩下的几十个
- **别人**：文献里结论最一致的就是这条线：测序工具（Exomiser）先排，大模型再重排。DeepBD 把 Exomiser 的 49.0% 提到了 65.8%；LA-MARRVEL、RareCollab 在 UDN 的真实病人上都胜过 Exomiser。Monarch 的 PhEval 是这类评测的标准做法

### D7 主要输在"选"，不在"找"

- **看到的**（第 29 章第 7 步）：几路名单合起来，前 10 名里有正确答案的比例，远高于最好的第 1 名：

  | 来源 | 几路名单合起来的前 10 名 | 最好的单个系统第 1 名 |
  |---|---|---|
  | 留出集 | 62.3% | 42.4% |
  | HMS | 62.5% | 37.5%（v1.1，练习） |
  | RAMEDIS | 86.5% | 32.7%（直接猜） |
  | MME | 87.5% | 80.0% |
  | 时间外推 | 46.8% | 25.5% |

  直接猜对、v1.0 错的题里，v1.0 自己的前 10 名里就有正确答案：HMS 15 道里 12 道，RAMEDIS 97 道里 85 道
- **原因**：最后怎么在候选里选，全靠模型读完证据凭感觉定。README 里记着，换三种办法让模型重新判断（证据表、复查排名、思考模式）都没赢过原来的判断：同一个模型换个提示词再判，还是同一个毛病
- **别人**：把"怎么综合各方证据"做成算得出来的东西。LIRICAL 用似然比，Exomiser 把几个分数合成一个，LA-MARRVEL 让模型判几次再投票，RareScale 专门训练了一个提名候选的模型

### D8 病人的资料太少

- **看到的**：agent 只拿到 HPO 编号和性别（[`evals/systems.py`](../src/raredx/evals/systems.py) 的 `Question`）。没有年龄、起病年龄、家族史、是否近亲结婚、化验数值，也没有"明确没有"的症状
- **原因**：一开始按 Phenopacket Store 和 RareBench 的格式定的输入，它们本来就只有这些
- **别人**：医生做鉴别诊断最常用的恰恰是这些：X 连锁的病出现在女孩身上要打折，新生儿起病和成年起病指向完全不同的一批病。liteOdyssey 专门有一步"对照这个病应有的表现和病人的实际表现"。DeepRare 直接读自由文本

还缺的：**医院真实病历当考卷**。MIMIC-IV 的数据协议不允许发给 deepseek 的接口（PhysioNet 2025 年 9 月的说明），这一版先不做，列进第 7 节。

### 5.2 新架构

```
病人资料：症状 + 年龄、起病年龄、性别、家族史 + 明确没有的症状
  │
  ▼
① 提名（几路同时跑）
   模型自己的知识 │ HPO 症状排序（Mondo 统一 OMIM 和 Orphanet）│ 相似病人
   → 合成一个候选池
  │
  ▼
② 逐个核查（agent 决定每个候选查什么）→ 每个候选一行证据：
   谁提名的、排第几；吻合、缺少、矛盾的症状；标注了几条；
   患病率；起病年龄、遗传方式对不对得上
  │
  ▼
③ 模型复核做主（第 30 章改过）
   模型读每个候选的证据行，排出前几名
   学出来的分数不代替它，只用来：估计把握程度；有同一来源的少量标注病例时，试按来源校准
  │
  ▼
④ 追问
   前两名分不开 → agent 找出最能区分它俩的症状 → 去问 → 回到 ②
  │
  ▼
输出：排名 + 把握程度（看前两名分数差多少）+ 理由 + 建议下一步查什么
```

- **agent 在哪里做决定**：② 每个候选查什么；④ 两个病分不开时，问什么、要不要退回去补查。这些是业界的标准做法：多路并行、"核查—再核查"的循环。实现上改用 LangGraph（最早的总体计划就是它）
- **③ 原来的设想和第 30 章的结果**：原来想像银行算信用分那样，从数据里学每项证据的分量，按分数选第一，代替模型凭感觉。第 30 章用已记下的考试离线试了：同一来源学、同一来源用，能到 35–45%；**换一个来源就掉到 20% 多，四个来源上都不如 v1.1**。学到的分量偏爱"记得全的极罕见病"，在单基因病的来源上对、在门诊病人上错，几个来源要的东西方向相反。所以不拿它代替模型的判断
- **把握程度看分差**：罕见病选择性预测那篇论文发现，第一名自己的分数靠不住，它领先第二名多少才靠得住
- **为什么不做"分诊"**：先判断"这个病人像单基因病还是常见病"再走不同的路，判错一次整条路都错。它想回答的"什么时候信模型、什么时候信工具"，落到每个候选上（谁提名的、多常见、记了几条症状），写进证据行交给模型复核更稳。第 30 章也说明：用数据学一套固定分量来回答它，换个来源就失灵

**第 34 章新外部卷的规矩**：
- 来源：PubMed Central 开放获取里，模型截止日（2025-06-01）以后发表的罕见病病例报告；用原文自由文本，经读病历那一步变成 HPO
- 按 Orphanet 患病率分层抽，"十万分之一以上"那一档不少于三分之一
- 答案：论文写明的确诊，对到 Mondo / OMIM / ORPHA 编号。程序先对，对不上的和随机抽查的由人核对
- **在谁都没看之前**按固定种子切成 60 道调试、240 道考试；清单和校验码提交到 git
- 老实说它不是什么：它仍然是发表的病例，不是医院里的真实病人

### 5.4 主要问题

> **在新外部卷的 240 道考试题上，v2.0 的第 1 名命中率，是否高于同一个模型直接猜。**

次要（都报，不管好坏）：

- 对 v1.1、v1.0、固定流程、LIRICAL
- 按患病率分档报；**最常见那一档上，v2.0 不能显著输给直接猜**（v1.0 就是输在这里，单独作为底线检查）
- 只看高把握的题，对多少
- 前 10 名；每道题的花费和用时
- 时间外推、留出集（标明同源）

v1.0 原来的主要结论（agent 对固定流程）在外部卷上不成立，这个结果照旧留在 `external_plan.md` 里，不改写。

### 5.5 判分

- **主要**：按编号严格判分，经 Mondo 认 OMIM 和 ORPHA；只认"完全对应"，上下级不算
- **宽松判分**：裁判换成另一家公司的模型（不再用 deepseek），所有系统用同一个提示词。用哪家、钱从哪出（OpenRouter，或者 AWS 上的模型），第 36 章前定
- **人工**：裁判和编号判分不一致的题里抽 50 道核对

### 5.6 风险

- **打分层学到某一个来源的习惯**：第 30 章证实了，学出来的打分换来源就失灵，所以不再用它排序；只用于把握程度和按来源校准，而且都要用轮流留出检验
- **追问只能模拟一部分**：病例记录里没写的症状，只能回答"没记录"，和真实门诊不一样，报告里写明
- **成本**：一道题的花费会是现在的好几倍，要量出来写进报告
- **加进 Orphanet 后留出集略掉**：留出集几乎全是 OMIM 病，多出来的相近的病可能把正确答案挤下去。第 31 章盯 dev-200

## 6. v3.0：症状加真实变异

### 6.1 考卷
照 Monarch 的 PhEval 的做法：Phenopacket Store 的病例报告里写了真实的致病变异，把它插进一份正常人（比如 1000 Genomes 里的一个人）的外显子测序数据里，造出"像真的测过序的病人"。PhEval 在 Zenodo 上公开了这样做好的数据，先看能不能直接用。

### 6.2 系统
- **先排**：Exomiser 14（官方 Docker 镜像支持 Mac 的芯片）读变异和症状，排出前 20 个候选基因。**它的数据（全量约 80 GB）放在 AWS 上**：在法兰克福开一台机器，数据直接下到那台机器和 S3，只把排好的名单传回本机（本机只剩约 60 GB）
- **再重排**：agent 拿到这 20 个候选，多两个新工具：
  - **变异证据**：人群频率、ClinVar 记录、致病性预测，按 ACMG 判据归类。判据的代码从旧仓库连同测试一起搬过来
  - **基因和病的关系有多可靠**：ClinGen 的评级
- **对照组**：Exomiser 单独；LIRICAL 带变异；现在的按基因排名；同一个模型拿到变异列表直接猜；v2.0

### 6.3 主要问题
> **在留出病人上，agent 重排以后的第 1 名命中率，是否高于 Exomiser 单独。**

### 6.4 动手之前要先解决的
1. **AWS 上的机器和花费**：先量清 Exomiser 数据的实际大小和每小时花费
2. **泄露**：ClinVar 里可能有题目自己那篇论文提交的变异记录，等于把答案告诉了系统。要么按日期遮（只用那篇论文发表之前的 ClinVar 版本），要么按出处删。没解决就不考

## 7. 不做的，和理由

| 不做 | 理由 |
|---|---|
| 多 agent | 文献里单 agent 和多 agent 几乎一样（48.5% 对 50.0%），我们的问题不在这里 |
| 硬性分诊 | 判错一次整条路都错；改成把候选的来源、患病率写进证据行，交给模型复核 |
| 换更大的模型当主模型 | DeepRare 发现换主模型影响很小；保持 `deepseek-flash`，各版本才能在同一个模型上比。只在消融里试"最后复核换强一点的模型"值不值 |
| 微调、强化学习 | 没有证据表明瓶颈在模型本身；先把知识、数据和"怎么选"修好 |
| 医院真实病历（MIMIC-IV） | 数据协议不允许发给 deepseek 的接口；换成本机模型或不留存数据的服务以后再考虑 |

## 8. 规矩（沿用，加一条）

- 每个版本的考试方案考前写好、提交；每份考卷，每个版本只考一次
- 输了照实写；原来的结论不改写
- **开发时每个来源分开看，不许只看一个总分**（新加）
- 新的花钱方式先在 ci-20 上试，量出单价再定上限
- 不同时跑两场考试（MLflow 的记录存在 SQLite 里，两场同时写会丢记录）
- 一次一个 PR，从最新的 main 开分支；每考完一次，把 `mlflow.db` 备份到 S3

## 9. 我的预期（写在动手之前）

- **第 30 章的离线试验能说明方向**：如果连用已有证据校准打分都胜不过现在的 agent，打分层这条路就要改。（2026-10-21 实际：胜不过，已改）
- **加进 Orphanet 对 HMS 帮助最大**：那 24 道注定答不对的题，大部分会变得能答
- **新外部卷上，v2.0 胜过直接猜**，主要胜在最罕见的那几档；最常见那一档大约打平
- **留出集上 v2.0 和 v1.1 差不多**，也可能因为多了相近的 ORPHA 病略掉一点
- **v3.0 胜过 Exomiser 单独，但幅度比 DeepBD 小**
